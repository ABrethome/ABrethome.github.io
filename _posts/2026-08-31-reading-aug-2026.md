**Title: AI Security**

[Link](https://newsletter.marinawyss.com/ai-security)

Summary: The newsletter focuses on the practical risks of deploying AI systems: prompt injection, data leakage, model misuse, and weak governance. It argues that securing AI is not just about model safety but also about protecting pipelines, tools, and enterprise data from misuse and supply-chain vulnerabilities. The central message is that organizations need guardrails, observability, and clear operational controls to make AI adoption safer and more trustworthy.

Key take away notes:
- Rate limits should be enforced per user rather than per IP address, because IPs are easy to rotate and do not reliably represent a real actor.
- Constrain the system's runaway costs and behaviors by limiting:
  - input length
  - maximum output tokens
  - amount of conversation history sent
  - number of retrieved chunks
  - number of agent loop iterations
- Agents are the riskiest pattern because a single request can trigger unbounded spending if there are no stop conditions.
- Run automatic attack testing during deployment to catch unsafe behaviors before they reach production.
- Before building anything, answer three core questions:
  - What internal data can this system see?
  - What text from outside can reach it?
  - What actions can it take, and what data can it send outside your system?
- This is known as the “lethal trifecta.” A system becomes especially risky when it can:
  - access private data,
  - ingest external text, and
  - send information back out.
- Meta's “Rule of Two” is a useful design heuristic: an agent should have at most two of those three capabilities in a single session.
- Examples:
  - It can read private data and take actions, as long as external text never reaches it.
  - It can read external text and take actions, as long as no sensitive data is accessible.
  - It can read private data and external text together, as long as it can only respond to the user and not take actions.
- If possible, design each agent so it has only two of the three capabilities.
- If an agent truly needs all three capabilities, Meta’s guidance is that it should not run autonomously; a human should approve its actions.

**Title: Bayesian Guardrails for AI Decisions: Measuring Uncertainty Before Automating Decisions**

[Link](https://towardsdatascience.com/bayesian-guardrails-for-ai-decisions-measuring-uncertainty-before-automating-decisions)

Summary: AI shouldn't automate from point estimates. Bayesian methods give posterior predictive distributions capturing aleatoric (inherent data/process variability) and epistemic (limited knowledge or model uncertainty) uncertainty, enabling rules—automate, review, abstain—based on expected loss, reversibility, and tail risk. Guardrails need calibrated uncertainty, continuous monitoring, and complementary methods (e.g., conformal prediction).

**Title: How to Fine-Tune an LLM: An End-to-End Guide**

[Link](https://towardsdatascience.com/how-to-fine-tune-an-llm-an-end-to-end-guide/)

Summary: This article argues that fine-tuning is the right move when you need an LLM to follow rigid, high-stakes formatting or decision rules reliably, not just answer generally. Using a real medical-reporting case, it shows that prompt-only or RAG approaches fail on complex branching logic, while QLoRA fine-tuning on a 7B model boosted accuracy from about 35% to 98% at far lower cost. It explains when to use RAG vs. fine-tuning, the intuition behind LoRA/QLoRA, and practical steps for creating data, training efficiently on a consumer GPU, and evaluating with a custom validation harness. The key takeaway: fine-tuning is for precise, repeatable behavior; RAG is for up-to-date facts.

**Title: 10 Context Engineering Techniques Every AI Engineer Should Know**

[Link](https://ai.plainenglish.io/10-context-engineering-techniques-every-ai-engineer-should-know-b54b486a6921)

Summary: Better context beats better prompts: deliver curated, compressed, and validated context before the LLM. Standouts: context compression to cut tokens and hallucinations; ranking plus metadata filtering to send only high-quality, relevant docs; dynamic context windows and deduplication to balance cost vs. complexity; plus hierarchical retrieval, caching, structured formatting, and validation so the model gets concise, fresh, trustworthy info. Nothing groundbreaking, but a nice summary good practices related to context management.

**Title: How does Claude watermark text?**

[Link](https://www.intoai.pub/p/how-claude-watermarks-text)

Summary: Anthropic watermarks Claude outputs (to satisfy EU transparency) using a SynthID-Text–style approach that changes sampling, not model weights. A secret key plus recent context seeds functions that score tokens; tournament sampling chooses winners, producing detectable token-patterns. Detection rebuilds seeds per position, averages scores, and compares to a threshold. Watermarks don’t reduce quality or embed hidden characters; full rewrites remove them.

**Title: How to Get More Statistical Power from Fewer Research Participants**

[Link](https://towardsdatascience.com/increasing-statistical-power-with-more-problems/)

Summary: The article demonstrates how researchers with limited participant pools can boost statistical power without adding more people. By pairing a within-subjects design (where each subject completes multiple conditions) with multiple tasks/problems per condition, outcomes can be analyzed as semi-independent data points using crossed statistical corrections. It also introduces PIPS (Project Impossible Power Simulation), an open-source Monte Carlo tool to calculate required sample and task counts.

**Title: Coding Agents Don’t Need Bigger Context Windows — They Need a Context Compiler**

[Link](https://towardsdatascience.com/coding-agents-dont-need-bigger-context-windows-they-need-a-context-compiler/)

Summary: The article argues that expanding LLM context windows causes attention dilution, higher costs, and lossy context compaction. Instead, it proposes a "Context Compiler" - a deterministic pipeline that pre-processes source code like a traditional compiler. By resolving dependencies, stripping implementation details down to interfaces, and discarding unreachable code across passes, the author's open-source Python tool reduced prompt token sizes by 69–74% in under 75 ms. This philosophy could be used for any retrieval, not just coding.
